# GPU速度とAIキャッシュの調査・改修

2026-10-10、RTX 2070 8GB / i7-9700K / RAM32GB、LiteRT-LM API 0.18.0 / Pillow12.3.0、WindowsネイティブWebGPU/D3D12。追加パッケージ・モデル・ドライバーの導入なし。

## 保護対象と測定方法

開始時の実インデックスは登録1,624枚、解析済み512枚、未処理1,112枚。ユーザー申告の約1,000枚は完了件数とは異なる。実DBはmode=roで参照し、解析再開・再走査・チェックポイント操作を行わない。実モデルを読み取り参照し、モデル本体はコピーしない。解析は専用 `data/performance-audit/<label>/index.sqlite3` へ保存。実AIキャッシュとは別の測定用キャッシュを再利用した。

同じ解析済み24枚をID順に均等抽出し、ウォームアップ後に3回測定。改修前はGit `e9bb9ea` のworkerを隔離ディレクトリへ読み出して実行。中央値を比較。最後に改修版で512枚全件を連続測定した。読込・デコード等の診断は別の24枚測定。ユーザーの既存ベクトル全件の集約SHA-256は各測定前後で一致し、改修版が生成した512件のfloat32ベクトルも既存値と完全一致した。

モデル初期化・フォルダー走査を除いた解析区間の速度。アプリの速度表示は初期化・走査を含むため同じ数値にはならない。OSファイルキャッシュを強制破棄しない。測定中にビルドや他のAIテストを並行実行しない。別実行の製品24枚測定は2.64枚/秒だったため、速度は負荷・キャッシュ・実行条件により変動する。試作方式の3.25枚/秒を製品の最終値に流用していない。

## 改修前後の実測

| 項目 | 改修前24枚×3回 | 改修後24枚×3回 |
|---|---:|---:|
| 解析速度の中央値 | 1.539枚/秒 | 3.178枚/秒 |
| WorkerピークWorking Set（RAM常駐量） | 693.73 MiB | 737.21 MiB |
| WorkerピークPrivate Commit | 4.192 GiB | 4.217 GiB |
| GPU平均稼働率（3回の平均） | 40.8% | 82.0% |
| GPU全体の最大メモリ | 3127 MiB | 3095 MiB |
| AIキャッシュ | 298.17 MiB | 298.17 MiB |

速度は2.07倍、約106.5%改善。RAM増加は約43.5 MiB。GPUメモリはnvidia-smiのアダプター全体で、他アプリも含む。GPUメモリ削減を最適化効果として主張しない。RAMは0.1秒間隔、GPUは0.2秒間隔でサンプリングした最大値。極短い瞬間的なピークは観測できない場合がある。Private CommitはRAM常駐量と同義ではなく、ネイティブ/ドライバー関連の確保も含む。

512枚連続：155.46秒、3.293枚/秒。ピークRAM 742.23 MiB、Private Commit 4.223 GiB、GPU全体3215 MiB、GPU平均87.2%、最大温度69℃。キャッシュ8ファイルのサイズは変わらなかった。約2.6分の試験であり、一晩の稼働やVRAM不足・スリープ復旧を検証した結果ではない。

## 時間内訳と原因

改修前の代表回：AI用画像準備182.42ms/枚、サムネイル用158.58ms/枚、AI API呼び出し292.42ms/枚。写真を2回デコードして、GPUとCPU準備を直列に実行していた。改修後の代表回は両画像の準備224.27ms/枚をGPU API呼び出し300.00ms/枚と並行実行。モデルのGPU呼び出し自体を約半分にした変更ではなく、GPU待ち時間を減らした変更。

別診断の平均：ファイル読込13.84ms、JPEGデコード134.10ms、EXIF/RGB44.06ms、AI縮小85.05ms、AI JPEG符号化4.55ms、サムネイル縮小42.48ms、同符号化0.67ms。診断はread_bytes→BytesIO→loadの分割計測で製品と呼び出し方/実行条件が異なるため、その総和を製品の前処理時間に置き換えない。24枚の符号化後バイトは旧前処理と一致。

AI API時間はJPEGのネイティブ前処理・転送・GPU処理・同期・結果返却を含む。純粋なGPUカーネル時間を独立に計測した値ではない。Python側の読込/デコード/前処理と区別した値。SQLiteは2回のFULLコミット合計が約1.8～2.3ms/枚、SQL自体も1ms未満/枚。保存バッチ化は必要性がなく見送った。

EはUSB接続I-O DATA HDCX-UT。MediaTypeはOS上Unspecifiedで、HDD/SSDを断定しない。ウォーム読込は約481 MiB/秒で、今回の大きな待ちはデコード/縮小にあった。連続解析中の単一ディスク計測ではEの物理読込0、DiskTime9%を観測したが、これは全期間の統計ではない。物理キャッシュが冷えたUSB/ネットワークドライブでは別途測定が必要。PC全体CPU使用率の低さだけでは、1本の前処理スレッドによるGPU待ちを否定できない。

GPUバッチ/先読みは旧版に未実装。現行ランタイムのバッチAPIも内部で逐次推論を繰り返す実装なので、APIをバッチ版へ変えるだけでは真の並列GPU推論にならない。[公式v0.18.0実装](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/executor/embedding_litert_compiled_model_executor.cc)。今回GPUエンジンを複数起動しない。

108枚時点の申告298.2MBと、今回の512枚完了時点298.17MiBは整合する。別DBで512枚再解析しても増加しなかった。同一モデル/GPU設定で写真枚数に比例するキャッシュではない。モデル名/更新日時/サイズ、バックエンド、ドライバー等が変わると別キャッシュや再生成があり得る。

## 初回・再解析・検索・削除

12枚の画像をRAMで前処理してから測定したAI APIの速度。全体解析速度とは区別する。初回はモデル読み込みだけで8ファイルすべて生成され、その後の最初の日本語検索と12枚解析でサイズは変わらなかった。通常キャッシュ実験は同じ隔離ディレクトリでエンジンを閉じてから再利用/削除。保存なし実験は別の空ディレクトリ・新規プロセスで実施。

| 状態 | モデル初期化 | 最初の日本語クエリ | 準備済み画像のAI API速度 | キャッシュ初期→解析後 |
|---|---:|---:|---:|---:|
| initial_empty | 9.68秒 | 1.03秒 | 3.04枚/秒 | 0.00 → 298.17 MiB |
| warm_reopen | 2.73秒 | 0.93秒 | 3.34枚/秒 | 298.17 → 298.17 MiB |
| after_cache_delete | 9.52秒 | 0.92秒 | 3.25枚/秒 | 0.00 → 298.17 MiB |
| no_cache | 6.26秒 | 1.05秒 | 3.18枚/秒 | 0.00 → 0.00 MiB |

削除しても、モデル本体/SQLiteベクトル/検索対象は保持。検索精度に関わるベクトルは同じで、通常再生成と保存なしの最大差は元float32丸め分約1.45e-8。写真の再解析は不要。次のAI処理でモデルを初期化し直すため、暖まったキャッシュ利用時の約2.7秒に対し削除後は約9.5秒。検索結果のコサイン計算と既存ベクトル自体は同じ。画像1枚あたりの定常GPU推論は大きく変わらず、キャッシュ維持が初期化短縮に有効。

SDKの`:nocache`は既存キャッシュを自動削除する指定ではない。空の専用ディレクトリを使った再試験で、読み込み/日本語検索/12枚解析後も0 bytesを確認した。上限時の退避に使用し、通常は298MiBを維持する。

AI入力JPEGと縮小サムネイルの準備データはRAMで処理し、AI用中間画像をディスクへ蓄積しない。写真数比例のサムネイルは別の512MiBキャッシュ。ベクトルはSQLite。DB/WALをAIキャッシュと混同しない。

## 必要性を確認して行った変更

- 1回のEXIF/RGB処理から1024px画像と320pxサムネイルを作る。JPEG95、トークン設定、768次元、正規化、モデルプロファイルを維持。
- CPU先読み1スレッド、圧縮済み2件まで。現在の1件と生成中の1件を含めても件数が限定される。キューに元のフル解像度ピクセルを保持しない。
- 先読み時はpendingのまま。消費時にprocessingへ変更。停止時に先読みを破棄しても永続キューから再開でき、1枚ごとのFULLコミットは維持。
- 前処理の前後とGPU処理前後で更新日時/サイズを確認して、準備後に変更されたファイルのベクトルを保存しない。
- 保存先の空き64MiB未満なら新しいジョブをprocessingにせず停止。空きを確保して再開できる。検査直後に別プロセスが容量を使うケースまで保証する予約機構ではない。
- AI処理の完了境界でキャッシュを計測し、使用中モデル分を除いて古いSDK生成物を整理。現モデル分だけで1GiBを超えたら、AIロック内でエンジンを閉じてから生成物を整理し、そのセッションを保存なしへ切り替える。設定に理由を表示。再起動/モデル設定変更/明示削除後には通常キャッシュへ戻る。

旧1GiB上限は起動/設定/closeの間だけのベストエフォートだった。Rustは親終了時にWorkerを終了させるため、Python closeが必ず走るとは限らず、解析中の超過も防げなかった。新しい方式は各成功AI処理/解析保存境界でも確認する。生成中の瞬間的な超過を防ぐ厳密なファイルシステムquotaではなく、SDK生成に失敗した場合などは次回起動で整理する。未知のユーザーファイルとリンクは削除/追跡せず、上限・容量表示は認識したSDK生成ファイルに適用する。モデルとDBを上限整理の対象にしない。

上限テストは小さな閾値で同じ分岐を通し、使用中ファイルを残す/エンジン解放後に整理/同一プロファイル/:nocacheへの切替を検証。実環境で意図的に1GiBのSDKキャッシュを生成した試験ではない。通常の298MiBが512枚後も増えないことは実測済み。

## 写真数別の容量推定

同じモデル・GPU・写真傾向での推定。原写真の容量は含めない。モデル本体は別に固定462.17MiB。SQLiteには768次元float32の3KiB/枚が必須。SQLite全体は隔離512件の終了後DB 2,506,752 bytes＝4896 bytes/枚を外挿。短い24件DBは固定ページの影響が大きいので使わない。1フォルダーの測定であり、多重フォルダー所属/パス長/旧プロファイルで変動する。通常WAL約4MiB等は別。

| 写真数 | AIキャッシュ | ベクトル実体（SQLite内） | SQLite全体概算 | サムネイル（512MiB制限あり） |
|---|---:|---:|---:|---:|
| 10,000枚 | 298.17 MiB | 29.30 MiB | 46.69 MiB | 289.76 MiB |
| 100,000枚 | 298.17 MiB | 292.97 MiB | 466.92 MiB | 512.00 MiB |
| 1,000,000枚 | 298.17 MiB | 2929.69 MiB | 4669.19 MiB | 512.00 MiB |

SQLiteとベクトル実体は足し合わせない。100万枚のSQLiteは約4.56GiB、AI約298MiB、サムネイル最大512MiB。実測平均サムネイル30383 bytes/枚を制限なしで外挿すると、1万枚約290MiB、10万枚約2.83GiB、100万枚約28.3GiBになるが、現アプリは512MiBまで整理し必要時に元画像から再生成する。ベクトルは消さない。数万件～100万件を実際に解析/検索した測定ではない。現在の全件コサイン検索の速度がこの規模でも実用的であると保証する推定ではない。

開始時の実SQLiteは本体2,899,968 bytes + WAL4,152,992 + SHM32,768。表示はこれらの合計。108枚時の4.5MBをそのまま写真枚数で掛けない。512枚の実サムネイル15,556,144 bytes。キャッシュ上限はサムネイル/AIに作用し、必要なSQLiteベクトルには適用しない。

## 再現方法と証拠

アプリの解析を一時停止し、GPUを使う他の試験を同時に走らせない。既存の解析済み写真が2枚以上必要。各labelは未使用の名前にし、上書きを避ける。countは最大1024、既存の解析済み件数が上限。保存済み写真が切断/変更されている場合は測定エラーとなる。測定は実DBを読み取り専用で参照する。

```powershell
cd PROJECT_ROOT
. ./scripts/env.ps1
./tools/python/Scripts/python.exe scripts/benchmark-pipeline.py --label before_next --worker-ref e9bb9ea --variant baseline --count 24 --runs 3
./tools/python/Scripts/python.exe scripts/benchmark-pipeline.py --label after_next --variant production --count 24 --runs 3
./tools/python/Scripts/python.exe scripts/profile-image-stages.py
./tools/python/Scripts/python.exe scripts/test-pipeline-safety.py
./tools/python/Scripts/python.exe scripts/test-worker.py
./scripts/build.ps1
./tools/python/Scripts/python.exe scripts/test-checkpoints.py
```

キャッシュ実験は `scripts/audit-cache-behavior.py` と `--no-cache-only`。既存の実験領域を上書きしないため、この実験だけは同じ既定名が存在すると停止する。測定用の既存領域を勝手に削除しない。

証拠JSON/logは `data/performance-audit/`（Git対象外）。最終比較は `baseline_verify.json` / `production_verify.json`、継続は `production512.json`、内訳は `image-stages.json`、キャッシュは `cache-behavior.json` / `cache-behavior-nocache.json`。個人写真のパスを含むDB/証拠をGitへ入れない。測定用に作ったSDKキャッシュは試験終了後に整理し、実アプリのキャッシュは保持する。

## dev.2の正確な検索とページ表示（2026-10-10）

合成768次元SQLite、同じ問い合わせ/同じDBをdev.1（3ea644b）と比較。AI埋め込み生成・モデル初期化は計測に含めない。OSの物理冷却キャッシュを保証するcold-start測定ではない。CPython更新前の実行は10万件6.006953秒→1.264236秒（4.751倍）、1万件0.622798秒→0.203313秒。別実行の10万件は1.321652秒で、約1.3秒の範囲。キャッシュ済み5ページ取得は計0.007444秒。

Pythonの要素ごとの内積を、同じdouble補償和を行うCRT不要の小型C DLLへ変更。近似検索やベクトル変更を行わず、1200個のランダム内積は従来Python sumとビット一致。全10万候補のスコア/ID順、全先頭1000件、後方ページ、同点境界、フィルター対象全体、無効化/最終走査消失を照合。旧heapには1万件の同点境界でID昇順の上位1000を保持しない問題が再現し、修正した。

1,000件で打ち切る旧キャッシュを廃止。全候補のスコア/IDだけを保持し、10万件のRAMオブジェクトサイズ12,400,984 bytes（11.83MiB）実測。ベクトルと全件写真情報をRAMキャッシュせず、ページ分だけSQLiteから読む。DBは約793MiB（WALを含む合成DBサイズ）で、実写真10万枚の解析性能やメモリ実測ではない。百万件の性能は未測定。AI画像処理・先読み・1枚ごとのSQLite保存は変えていない。AIキャッシュ1GiB上限を維持する。

証拠: data/release-tests/rc-audit/exact-search.json、再現: scripts/build-search.ps1 → scripts/test-exact-search.py（E側の使い捨て合成DB）。補助DLLがない/壊れている場合は正しいPython sumへ戻るため、その場合の初回検索は遅くなる。

### CPython 3.14.8 / OpenSSL 3.5.9更新後の再測定

2026-10-10。同じ新runtime上で旧dev.1 Libraryソース（3ea644b）と改修版を比較。1万件0.674568→0.127299秒（5.299倍）、10万件6.910913→1.335906秒（5.173倍）、キャッシュ済み5ページ合計0.008133秒。全候補/後方ページ/フィルターの正確性と1,200内積のビット一致を再確認。これは同じruntimeでの実装比較であり、旧配布Pythonの速度を再測定した値ではない。全順位キャッシュ11.83MiB、DB+WAL831,208,528 bytes。測定条件のAI生成/モデル初期化/OS cold-cacheの制約は上記と同じ。
