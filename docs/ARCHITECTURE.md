# 技術設計

## 境界

- `src/`: Lit UI。AIモデルやSQLiteを直接扱わず、型付きRPCのみ。
- `src-tauri/`: Tauri 2ウィンドウ、ネイティブ選択ダイアログ、Workerの起動、許可メソッドの検証、登録済みファイルのOS起動。
- `worker/ai.py`: AIバックエンドの契約、前処理、LiteRT-LM実装。将来ここへ別ランタイムを追加。
- `worker/database.py`: SQLiteスキーマ、WAL、FULL synchronous、外部キー、トランザクション移行、将来移行時の整合バックアップ。
- `worker/prefetch.py`: 1スレッドで画像の読込・デコードを先読み。圧縮済み画像/サムネイルだけ2件までキューに保持。先読み段階は永続ジョブ状態を変更せず、停止時は破棄して次回再開。
- `worker/library.py`: 登録対象だけの走査、永続キュー、1画像ずつ解析、検索、サムネイル。
- `worker/main.py`: version 1 JSON-linesプロトコル。stdin/stdoutで通信し、待受ポートを開かない。
- `data/`: モデル/設定/DB/サムネイル/AIキャッシュ/WebView2データ/ログ。Gitとインストーラー対象外。
- `tools/`, `tmp/`, `target/`, `dist-worker/`, `node_modules/`: ローカルツールと成果物。ソース管理対象外。

## 実行方式

Windows版 `litert-lm-api==0.18.0` を実機で検証して採用。GPUはPythonからネイティブLiteRT-LM内のWebGPU/D3D12を利用し、WebView2内のJavaScriptでは実行しない。CUDA・PyTorch・TensorFlow本体・JS/WASMランタイム・追加モデルを導入しない。GPU実行がPythonで成立したため、JS/WebGPUへ切替える必要はなかった。TauriのWebView2は日本語UIとIPCの検証対象。

Workerの解析スレッドはUIから独立。AIロックで同時推論を抑制し、DBロックは短い保存トランザクションだけ。検索中のAI処理は解析との間で順番待ちになる。UIの描画や操作は継続。GPU異常はエラーを表示し、CPUを明示選択して復旧できる。Nativeランタイム自体が異常終了した場合は再起動し、`processing`キューを`pending`へ戻す。

Windows Job Objectで親アプリの終了時にWorkerを終了させる。二重起動は既存のウィンドウにフォーカスする。v1.0開発版はTauri親プロセスをトレイに維持して同じWorkerを所有する。ウィンドウを隠しても単一writerとJob Objectを維持する。独立サービス化は採用しない。将来の常駐WorkerではJob所有者を独立プロセスへ移し、名前付きパイプなどの認証付きIPCへ交換できる。GPU推論はWebView2の寿命に依存しない。ただしその独立プロセス形態は未検証。

## 検索データ

`folders`、`files`、`folder_files`（重複登録してもファイル/ベクトルは共有）、`models`、`embeddings`、`jobs`、`settings`。ベクトルはfloat32、L2正規化。モデル実ファイルSHA-256・出力次元・前処理バージョン・正規化・クエリprefix・ランタイムバージョンから互換プロファイルを生成。異なるプロファイルを比較しない。CPU/GPUは同じモデル空間として共有し、実行バックエンドをメタデータに記録する。

前処理はEXIF向き補正 → RGB → 縦横最大1024に縮小 → JPEG品質95 → モデル標準前処理。元ファイルへは書き込まない。クエリには公式の`task: search query | text:`prefixを適用。実機で768次元を観測し、固定値を仮定せず初回出力から記録。

追加・変更時に必要なファイルだけキューに入れる。正常な保存は写真ごとにコミット。中断・クラッシュ時は進行中の1件を再解析可能とする。アクセス失敗や途中走査は削除判定を確定しない。モデル・前処理の変更は新プロファイルだけ解析し、以前のベクトルは互換性を分離して保持。古いモデルプロファイルの任意削除UIは未実装。

## 拡張

動画は`files.kind=video`に加えて`segments(file_id,timestamp,...)`テーブルを移行で追加し、FFmpegが必要フレームだけ一時抽出。セグメント単位のキューとベクトル、必要サムネイルを保存。音声もセグメントと対応時刻を追加し、文字起こし保証とは分ける。常駐は現行永続キューを共有する単一Writer方式を維持。現在のSQLiteを複数Workerから同時に解析させない。

自動更新は将来Tauri updaterを追加可能。バージョンごとにデータ領域を複製しない。モデルはインストーラー資源と分離し、毎回のビルドでコピーしない。

## 容量管理

サムネイルは参照がないものと古いものを512 MiBまで整理する。消えたサムネイルは元画像から読み取り再生成する。AIランタイムキャッシュは `runtime-cache/<model-sha256>` に分離し、次のモデルを読み込む前に旧モデル分を整理、768 MiBの空きを確認する。エンジン解放・起動・設定変更・AI処理完了時には合計1 GiBを目標に古い生成ファイルを削除する。稼働中エンジンのキャッシュは削除しない。現モデル分が上限を超える場合はAIロック内でエンジンを解放してから現モデルの生成ファイルを整理し、同一プロファイルでSDKの`:nocache`へ切り替える。SDK内部の生成中には一時的に上限を超える可能性がある。親のJob Object終了ではPythonのcloseが呼ばれない場合もあるため、終了時整理だけに依存しない。保存先の空き容量64 MiB未満では次のジョブをprocessingにせず停止する。指定740mモデルではCPU/GPU両方で約670 MiBを観測した。未知のファイルやリンクは削除しない。設定のキャッシュ削除はエンジン解放後に行い、SQLiteベクトルとモデルは保持する。

初期版はモデル変更時の旧埋め込みプロファイルを保持する。古いプロファイル削除UIとDBサイズのユーザー指定上限は未実装。検索コーパスが増えると必要なベクトル分のDB容量も増える。

## v1.0開発の追加境界

`worker/model_download.py`は固定公式モデルの確認後取得とSHA検証、`diagnostics.py`は基本環境確認と別プロセスのGPU/CPU実行診断、`storage.py`は元を残すSQLite backup/ファイル検証コピー、`user_errors.py`は日本語案内。`src/release-controls.ts`は初回案内/ヘルプ/設定を担当。preferencesと再開希望は既存settingsに追加してスキーマv1を維持する。

dev.2は全候補の内積を正確に計算し、スコア降順/ID昇順の全順位をスコアとIDだけでRAMに保持する（10万件約11.83MiB実測）。ベクトルや全件写真メタデータはキャッシュせず、ページ分だけSQLiteから取得する。1,000件で打ち切らず、後方ページとフィルター対象を失わない。変更/走査/保存/設定と無効化は同じRLock内で確定する。走査完了時の消失判定でも無効化する。

Windows CPython 3.14の内積ループのみ小型C DLLに置き換え、float32インデックス×float64クエリの積と補償和を従来Python sumとビット一致させる。/fp:strict、FMA/並べ替え/量子化/近似探索を使わない。CRT依存とAVX要求なし。DLLなし/読み込み失敗/別Python環境はPython sumへ戻す。AI推論・画像先読み・SQLiteスキーマは維持する。

ログイン起動はHKCUのアプリ専用Run値でオプトイン。完全終了はshutdown後に最大15秒待ち、Job Object/強制終了で孤児を防止する。Windowsスリープそのもののフックは未実装で、SQLite FULL/WALと再開キューによる復旧を維持する。実スリープ試験は未実施。
